# Phase 5 — Wire FIDO2 to TROPIC01 (THE MIC-DROP)

> **Status:** Draft — awaiting user sign-off before M1 implementation.
> **Started:** 2026-05-11
> **Goal:** Real FIDO2 backed by real TROPIC01 chip keys. End-to-end working WebAuthn on `webauthn.io` from Firefox/Chrome.
> **Audience:** AI agents + future code reviewers (assume Yubico-class scrutiny).

---

## 0. Why "be extra careful"

Phase 5 is the first phase that produces **a security-claim-bearing artifact**. Phases 0-4 produced "a firmware that demonstrates the protocol works." Phase 5 produces "a firmware that, if you trust it, holds your WebAuthn credentials for real."

Three audiences to design for:

1. **Adversaries** — anyone with the binary will try to forge signatures, recover keys, replay PINs, downgrade the protocol. Defense lives in TROPIC01 (private keys never leave the chip), in TrustZone-M (Phase 6 future), and in correct protocol implementation (this phase).
2. **Hostile reviewers** — Yubico, FIDO Alliance, SoloKeys-alumni, security researchers. They'll look for: spec violations, side channels, novel-crypto-rolled, PIN-protocol bugs, weak randomness, monotonic-counter weaknesses, attestation-replay opportunities.
3. **Auditors** — `cpp-reviewer` (per phase), `nix run .#lint` (per phase), eventually external pen-test. The code must be small, named clearly, and easy to read line-by-line.

**Mantra:** if a decision is hard to defend in a code review, redo it.

## 1. Decision drift — proposed amendment to §2

**Re-amend Decision #7** (already once amended on 2026-05-11). Reason:

The 2026-05-11 amendment said "SoloKeys-derived ClientPIN + storage + extensions" referring to **files that don't exist** in SoloKeys' upstream repo. Actual layout:
- `solo/fido2/ctap.c` (~2 000 LOC monolith) contains MakeCred + GetAssertion + ClientPIN + extensions all in one file
- `solo/fido2/crypto.c` provides AES/HMAC/HKDF wrappers
- `solo/fido2/storage.h` exists, `storage.c` does NOT — storage is per-platform (`targets/stm32l432/src/device.c` for the upstream stm32l432 SoloKey)

Reading SoloKeys' actual `ctap.c` for Phase 5 reveals: it's 2019-era code, the company is defunct, it predates CTAP2.1, and it's tightly coupled to SoloKeys' own storage abstraction. **Vendoring it would be more work, not less, than writing our own.**

### Proposed Decision #7 v3 (amendment 2026-05-11 #2)

> **FIDO2 stack: hand-rolled C against FIDO CTAP2 specification (primary reference) + SoloKeys' `ctap.c` (secondary reference for known-good control flow). No SoloKeys code vendored. Same approach as Phase 4 — which produced clean, audited code at ~1 100 LOC vs SoloKeys' ~5 000 LOC for equivalent surface. Phase 5 adds ClientPIN protocol v1 (CTAP2 §6.5), credential storage (TROPIC01 R-mem), and authenticatorReset. ClientPIN protocol composes off-the-shelf primitives from `trezor_crypto` (AES-256-CBC, HMAC-SHA256, HKDF, X25519); the *protocol* is rolled but no novel crypto is invented. hmac-secret extension deferred to Phase 5.5 once core flow ships.**

**Why this is defensible at audit:**
- Smaller surface = easier review (1 100 LOC vs 5 000 LOC matters in audit budget)
- No 2019 SoloKeys CVEs inherited (`CVE-2020-12053`, etc.)
- All primitives are well-vetted upstream (trezor_crypto used by Trezor hardware wallets)
- Our CBOR is hand-rolled but already cpp-reviewer-audited (Phase 4 H1/H2/H3 fixed)

## 3. Threat model (what the big players will look for)

| Attack | Defense | Validated at milestone |
|---|---|---|
| Recover Ed25519 private key from binary | Keys generated by `lt_ecc_key_generate` inside TROPIC01; chip never exports privkey | M2 |
| Recover PIN from binary or RAM dump | PIN stored as SHA-256(PIN)[:16] in R-mem; verified via constant-time memcmp | M3 |
| Forge signature for unknown credential | credId is wrapped index → lookup fails → CTAP2_ERR_NO_CREDENTIALS | M2 |
| Replay an old signature to a different RP | Signature is over `authData‖clientDataHash` where authData contains `rpIdHash` — distinct per RP | inherits Phase 4 |
| Brute-force PIN | TROPIC01 MAC-and-Destroy consumes a slot per attempt; 8 attempts → permalock; 3 attempts → power-cycle required | M4 |
| Counter rollback (replay assertion at lower count) | Monotonic shared counter via TROPIC01 hardware counter; signCount in authData never decreases | M2 |
| Side-channel timing on PIN check | trezor_crypto's `memcmp` is NOT constant-time — must wrap with `sec_memcmp` (provided by libtropic_secure_memzero.c) | M3 |
| Side-channel timing on PIN encryption | trezor_crypto AES is not constant-time on ARMv7-M; on Cortex-M33 the SAES doesn't exist (decision #5) — this is a documented residual risk; mitigation = secret PIN never observable to firmware after first 64 ms of session | M3 (documented) |
| Power-loss mid-operation leaves corrupt state | Two-phase commit pattern: ECC slot generated first, then R-mem metadata written; orphan-slot scrubber on boot erases ECC slots without R-mem entries | M1 |
| Pairing-key compromise (SH0 keys are public) | Documented in §5: production deployments must rotate to SH1. Phase 5 stays on `*_prod0`. | not in scope (Phase 8) |
| Adversarial CBOR (length confusion, recursion) | Inherits Phase 4 audit fixes (H1/H2 size_t truncation); cpp-reviewer audit at end of Phase 5 covers new CBOR consumers | M5 |
| `authenticatorReset` accepted from a remote/web origin | CTAP2 §6.8: Reset MUST require user presence + power-cycle within 10s + first command since power-cycle. We enforce the 10 s window via boot-timestamp check. | M5 |
| Resident-key data exfiltration via brute-force credId | credId = 16 B random nonce; 2^128 search space; no info leakage in lookup-by-credId | M1 |

## 4. Architecture

### 4.1 TROPIC01 resource map

| Resource | Count | Phase 5 usage |
|---|---|---|
| **ECC slots** | 32 | Up to 32 credentials. Slot N holds one Ed25519 keypair, generated on chip. |
| **R-mem slots** | 512 × 475 B | Slot 0 = global state (PIN hash + retry counter index + allocation bitmap). Slots 1-32 = per-credential metadata (parallel to ECC slot index). Slots 33+ reserved for future (hmac-secret, OpenPGP card metadata Phase 7). |
| **MAC-and-Destroy slots** | 128 | Slots 0-7 reserved for PIN-attempt rate limiting. Each failed PIN consumes one slot in order. |
| **Hardware monotonic counter** | 16 | Counter 0 = global signCount source. All credentials read from this one counter; increment on every assertion. |
| **Pairing keys (SH0-3)** | 4 | SH0 with `*_prod0` defaults (decision #10). SH1-3 unused this phase. |

**Slot mapping invariant:** for credential `i` (0 ≤ i < 32), ECC slot index `i` ↔ R-mem slot index `i+1` (so R-mem 0 is reserved for global state).

### 4.2 R-mem slot 0 layout (global state, ≤ 475 B)

```
offset  size   field
------  ----   -----
   0      4    magic "NX5K" (0x4E,0x58,0x35,0x4B)
   4      2    schema_version = 1 (uint16_BE)
   6      4    bitmap of allocated credential slots (uint32_BE, bit i = slot i used)
  10      1    pin_set (0=no PIN, 1=PIN set)
  11     16    pin_hash_left = SHA-256(PIN)[:16]
  27      4    pin_retries_remaining (uint32_BE; written via R-mem; consumed via M&D)
  31      1    md_next_slot (next MAC-and-Destroy slot index to consume on next failed PIN; 0..7)
  32     16    md_keys_lookup[0..7]  -- one byte per M&D slot: 0=consumed, 1=available
  48      ...  reserved, zero-filled
```

**Why split PIN counter between R-mem and M&D:** R-mem write is the source-of-truth ledger; M&D consumption is the hardware-enforced rate-limit. Spec compliance requires the chip to refuse PIN attempts after the configured retry count even if firmware is replaced. M&D delivers that.

### 4.3 R-mem slot N+1 layout (credential N metadata, ≤ 475 B)

```
offset  size   field
------  ----   -----
   0      4    magic "NXCR" (0x4E,0x58,0x43,0x52)
   4      1    schema_version = 1
   5      1    alg (8 = COSE EdDSA / -8; reserved bit for future ES256)
   6      1    flags (bit 0 = resident; bit 1 = uv_required; bit 2 = backup_eligible)
   7     32    rpIdHash (SHA-256 of rp.id)
  39     16    cred_id_nonce (random)
  55      4    created_at (boot-counter; not wall-clock)
  59      8    last_used_signcount (uint64_BE)  -- for audit; signature uses global counter
  67     64    user_handle (variable len; first byte = len, then bytes; padded zero)
 131     34    rp_name (truncated; first byte = len)
 165     34    user_name (truncated; first byte = len)
 199    276    reserved + room for hmac-secret cred-protect data in Phase 5.5
```

### 4.4 credentialId format

```
[1 B version=0x01] [1 B slot_index 0..31] [16 B cred_id_nonce] = 18 B total
```

**Why this format (not encrypted wrap):**
- Resident-only model in Phase 5 — RP holds nothing secret about the credential
- 18 B is well under any RP's credentialId size limit
- `slot_index` is non-sensitive (just an enumeration); leaking it leaks nothing more than "this device has N credentials" which AAGUID + attestation already imply
- `cred_id_nonce` is the lookup tie-breaker (proves the RP actually saw this exact credential, not just guessed the slot index)

**Lookup:** read slot_index from credId byte 1; load R-mem slot (slot_index+1); compare nonce. If match, slot is valid.

**Decision deferred (Phase 6):** non-resident "wrapped credId" mode (Yubikey-style unlimited host-stored credentials). Requires a firmware-burned AES-GCM wrapping key with TrustZone secure-world storage. Phase 5 = resident-only; users get 32 credentials, which beats Yubikey 5 NFC (25 resident).

### 4.5 ClientPIN protocol surface (CTAP2 §6.5 v1)

| Subcommand | Action |
|---|---|
| 0x01 getRetries | Return `pin_retries_remaining` from R-mem slot 0 |
| 0x02 getKeyAgreement | Return ephemeral X25519 pubkey (generated at boot, regenerated after PIN op) |
| 0x03 setPIN | Decrypt newPinEnc via ECDH-derived AES key → store SHA-256(PIN)[:16] in R-mem slot 0 → reset retries to 8 → seed M&D slots 0-7 with random per-slot keys |
| 0x04 changePIN | Verify pinHashEnc → decrypt newPinEnc → update R-mem; reset retries |
| 0x05 getPINToken | Verify pinHashEnc + consume M&D slot → on success: generate fresh pinUvAuthToken (32 B random, RAM-only) → encrypt and return |

**pinUvAuthToken lifecycle:** RAM only, regenerated on every getPINToken call, valid until power-cycle. Lost on reboot — RP must re-PIN.

**PIN verification flow (the hot path, audit this carefully):**

```
1. Read pin_retries_remaining from R-mem.
2. If 0 → return CTAP2_ERR_PIN_BLOCKED.
3. If consecutive_fails_this_boot >= 3 → return CTAP2_ERR_PIN_AUTH_BLOCKED (until power-cycle).
4. Decrement retries IN R-mem FIRST (atomic write to slot 0).
5. Consume the M&D slot at md_next_slot via lt_mac_and_destroy:
     - Input: SHA-256(submitted_PIN)
     - Output: 32 B per-slot MAC
     - Compare MAC against the seed key written for this slot at setPIN time
        (the seed is in R-mem slot 0 md_keys_lookup table — TODO design how)
6. If MAC matches → PIN correct → reset retries to 8 → re-seed any consumed M&D slot
   for next use → return success.
7. If MAC mismatch → PIN wrong → md_next_slot++ → if md_next_slot == 8 →
   permalock (set pin_set=2, refuse all further PIN ops until Reset).
```

**OPEN QUESTION (resolve before M4):** the M&D primitive semantics — does `lt_mac_and_destroy` allow comparing against an expected output (i.e., is the seed key recoverable for comparison?), or does the chip return the output to firmware which then must compare? Both models are possible; spec lookup required. This determines the M&D usage shape.

### 4.6 authenticatorReset (cmd 0x07)

CTAP2 §6.8 conditions:
- MUST be issued within 10 s of authenticator power-on (we'll enforce via tick counter)
- MUST be the first or among the first commands after power-on
- MUST require user presence (Phase 5: stub-true per decision #3)

Reset action:
1. For each i in 0..31: `lt_ecc_key_erase(slot=i)`
2. For each i in 1..32: `lt_r_mem_data_erase(slot=i)`
3. `lt_r_mem_data_erase(slot=0)` (global state — also wipes PIN)
4. Optionally erase consumed M&D slots: cannot un-consume; just allocate new ones on next setPIN
5. Return `CTAP2_OK`

## 5. Milestones (each is one HW-validated commit)

### M1 — TROPIC01 slot manager + R-mem layout (no FIDO surface change)

**Deliverable:**
- `firmware/src/fido_hid/slots.{h,c}` — credential slot allocator over TROPIC01 ECC + R-mem
  - `slots_init()` — read R-mem slot 0; if magic mismatch → first-boot init (write fresh global state)
  - `slots_alloc(rp_id_hash) → int slot_idx (-1 if full)` — find free bit, claim, write R-mem
  - `slots_lookup_by_credid(credId, &slot_idx)` — verify nonce, return slot
  - `slots_erase(slot_idx)` — erase ECC + R-mem entry, clear bitmap bit
  - `slots_orphan_scrub()` — at boot, ECC slots without R-mem entry → erase
  - `slots_count_used() → int` — for getInfo (existingResidentCredentialsCount)
- Phase 5 host tool: `tools/phase5_inspect.py` — read raw R-mem slot 0 (via lt-rpc passthrough? OR a new dedicated debug HID command?) — used to verify slot manager works
- No CTAP2 changes — Phase 4 stub credstore still in place
- **HW checkpoint:** `nix run .#validate-phase5-m1` — initializes empty store, allocates 3 slots, reboots, verifies all 3 still listed, erases 1, reboots, verifies bitmap reflects state.

**Risk:** first phase that writes R-mem. R-mem writes are safe (rewritable, no brick risk per §5), but a bug in our layout would silently corrupt state. Mitigate by reading-back after every write in M1 (will optimize later).

### M2 — Swap credstore to TROPIC01 backend (THE MIC-DROP IS HERE)

**Deliverable:**
- Rewrite `credstore.{h,c}` to wrap `slots.h`:
  - `credstore_make_credential(rp_id_hash, alg) → (slot_idx, credId[18], pubkey[32])` calls `slots_alloc` + `lt_ecc_key_generate` + `lt_ecc_key_read`
  - `credstore_get_assertion_signer(credId) → slot_idx` calls `slots_lookup_by_credid`
  - `credstore_sign(slot_idx, msg, mlen, sig_out[64])` calls `lt_ecc_eddsa_sign`
  - `credstore_peek_signcount()` reads `lt_get_info_monotonic_counter(0)`; `credstore_commit_signcount()` advances it
  - Embedded stub seed bytes deleted from binary
- Adjust `ctap2_creds.c`:
  - `ctap2_make_credential` calls `credstore_make_credential` (new signature with rp_id_hash)
  - `ctap2_get_assertion` calls `credstore_get_assertion_signer(credId from allowList)` instead of returning the fixed stub credId
- Bump AAGUID to `6e697874726f70696300000000000002` (Phase 5 has behaviorally-different attestation; AAGUID change is per WebAuthn spec)
- **HW checkpoint:** `nix run .#validate-phase5-m2` — full Phase 4 suite passes, PLUS: MakeCred 3 times yields 3 distinct pubkeys; GetAssertion across the 3 credIds returns signatures verifiable against each respective pubkey; reboot dongle → repeat GetAssertions still work.
- **THE BIG TEST:** plug in dongle → Firefox → webauthn.io → register → log out → log in → success. Screen-record. This is the demo.

### M3 — ClientPIN protocol (RAM-only counter, no M&D yet)

**Deliverable:**
- `firmware/src/fido_hid/pin.{h,c}` — ClientPIN v1 implementation
  - Ephemeral X25519 keypair generation (`lt_random_value_get` → curve25519_keypair via trezor_crypto's `curve25519_donna`)
  - HKDF-SHA256 key derivation
  - AES-256-CBC encrypt/decrypt (trezor_crypto AES)
  - HMAC-SHA256 (trezor_crypto)
  - `pin_set(pin_plain[64], pin_len)`, `pin_change(old, new)`, `pin_verify_and_get_token(pin)`
- Wire `CTAP2_CMD_CLIENT_PIN` into dispatcher
- Wire PIN-token requirement into MakeCred + GetAssertion (when PIN is set, refuse without pinAuth)
- Retry counter in RAM only (will be MAC-and-Destroy-backed in M4)
- **HW checkpoint:** `nix run .#validate-phase5-m3` — setPIN, getRetries=8, changePIN, getPINToken with correct PIN, MakeCred-with-pinAuth, GetAssertion-with-pinAuth, all from Python harness. Wrong PIN decrements retries.

### M4 — MAC-and-Destroy-backed PIN retry counter

**Deliverable:**
- At first `pin_set`: allocate 8 M&D slots, seed each with random output (write seed key into R-mem slot 0 md_keys_lookup table — encrypted under HKDF(rpHash, "md")? open question)
- On each PIN verify: consume next M&D slot via `lt_mac_and_destroy(input=SHA256(PIN))`
  - Compare output against stored expected output for that slot
  - Match → PIN was correct; advance slot pointer is fine (next attempt consumes the NEXT slot)
  - Mismatch → PIN was wrong; slot is already consumed; advance pointer
- Lockout when md_next_slot reaches 8
- Reset clears M&D state (regenerate on next setPIN)
- **HW checkpoint:** `nix run .#validate-phase5-m4` — wrong PIN 7 times (counter goes 8→7→6→5→4→3→2→1), 8th attempt blocked, factory reset, can setPIN again.

**Deliverable:**
- Wire `CTAP2_CMD_RESET` (0x07) — enforces 10 s post-boot window
- Add `nix run .#validate-phase5` running all M1-M4 tests + reset + post-reset re-registration
- Add `nix run .#flash-and-validate-phase5`
- `STATUS.md` Phase 5 entry
- `cpp-reviewer` security audit on `pin.{h,c}` + `slots.{h,c}` (newly attack-surfaced — same cadence as Phase 3 / Phase 4)

## 6. Code-organization rules for Phase 5 (audit-friendliness)

- Each new file ≤ 400 LOC. Split if exceeded.
- No new global variables — all state in static functions or initialized-at-boot structs.
- Every function that touches a chip resource (ECC slot, R-mem, M&D) is documented with: which slot it touches, what error codes it can return, whether it's idempotent.
- Every PIN-related function has a comment block citing the CTAP2 §6.5 line number it implements.
- Constant-time comparison for ALL secret comparisons (PIN hash, pinAuth, pinUvAuthToken) using `lt_secure_memzero.h`-style memcmp wrapper.
- No `printf`/log statements in the PIN path (timing channel; verbose log statements have been observed leaking PIN state in real audits).
- No malloc anywhere.

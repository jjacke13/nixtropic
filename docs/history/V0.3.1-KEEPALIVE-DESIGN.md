# v0.3.1 — Design: CTAPHID KEEPALIVE

> **Working design for v0.3.1** (written 19 Oct 2026, for Jan's review). Becomes part of
> the frozen record when v0.3.1 is tagged. Current documentation:
> <https://jjacke13.github.io/nixtropic/>.

Backlog item 6.7. Evidence: usbmon captures of 18 Oct (`~/agents/jan/ref/m6-windows/`) and
Jan's analysis (`phase9-windows-fido-analysis.md`). Code read at 87e1d7f.

## 1. Problem

The dongle sends nothing on the FIDO interface between a CTAPHID_CBOR request and its
answer. Windows abandons a silent request: in the captures it re-INITs after 2.6 s on
getPinUvAuthToken (0x09) and after 6.6 s on changePIN, and our successful answer arrives
1–2 ms later on a channel Windows has left. Registration loops; a PIN change reports an
error although it completed. Linux clients wait and are not affected. Leading hypothesis
for why v0.2 worked: its PIN path was faster (to be confirmed by the KEEPALIVE-only Windows
test, Jan).

The numbers are not a Windows deadline (none is documented) and not a reason to make the
PIN path faster: a correct verify is 1 + 8 M&D calls, a change about 41 M&D calls plus the
checked record stores (Jan), and a touch wait lasts as long as the user takes.

## 2. What the specification says

CTAP 2.2 PS 2025-07-14 (and CTAP 2.1 the same):

- §11.2.9.1 *Mandatory commands* lists CTAPHID_KEEPALIVE (0x3B).
- §11.2.9.1.7: "This command code is sent while processing a CTAPHID_MSG. It SHOULD be
  sent at least every 100ms and whenever the status changes. A KEEPALIVE sent by an
  authenticator does not constitute a response and does therefore not end an ongoing
  transaction." Payload: one status byte, PROCESSING = 1, UPNEEDED = 2.
- §11.2.9.1.2 (CBOR) allows KEEPALIVE between request and response.
- §11.2.9.1.5 (CANCEL): a request that can be cancelled answers CTAP2_ERR_KEEPALIVE_CANCEL.

So: command mandatory, cadence SHOULD over USB (the BLE transport says SHALL, §11.4.9).
Do not quote 100 ms as a MUST or 2.6 s as a Microsoft deadline.

## 3. Today's code, the parts that matter

- `fido_hid_task()` (ctaphid.c:507) runs one complete request synchronously from the main
  loop: `s_busy_cid` = owner CID, `s_running` = executing. Nothing else is sent until
  `dispatch_request()` returns.
- During a touch wait `user_presence_check()` (user_presence.c:131) pumps `tud_task()`;
  CTAPHID then answers INIT, takes CANCEL for the running request, refuses the rest with
  CHANNEL_BUSY (ctaphid.c:420). No KEEPALIVE.
- Every chip command goes through one of the 14 L3 wrappers in tropic.c, and each starts
  with `tropic_l3_session_ensure()` (tropic.c:163), which also runs the handshake
  (cert store read + `lt_session_start`) when the session is off.
- Short replies during a request (INIT, BUSY) go out through `send_now()` (ctaphid.c:122)
  and are dropped if the IN endpoint is busy.
- Debug build only: lt-rpc requests run inside the USB callback (usb.c:185 →
  rpc.c `dispatch_request`), gated only by `user_presence_is_awaiting()` (rpc.c:163).
  CCID APDUs run only from the main loop (`usb_ccid_task`, never from a pump).
- ctaphid.h:19 says "0x12 CTAPHID_KEEPALIVE emitted by us when waiting for SW1 touch".
  Both halves are wrong (0x3B; never emitted). Fix the comment.

## 4. Design

One new function in ctaphid.c, called from two places.

### 4.1 `fido_hid_progress()`

```c
/* Between steps of a running FIDO request: send KEEPALIVE on its channel when due and
 * pump USB.  No-op unless a FIDO request is executing. */
void fido_hid_progress(void);
```

1. Return at once unless `s_running` (so OpenPGP chip work and the idle loop are
   untouched) and unless already inside it (static guard: no nesting).
2. Status = `user_presence_is_awaiting() ? UPNEEDED : PROCESSING`.
3. If the status differs from the last one sent on this request, or 50 ms have passed
   since the last KEEPALIVE (`HAL_GetTick`, unsigned difference so the tick may wrap),
   and the IN endpoint is ready: send one packet
   `CID = s_busy_cid, CMD = 0x80|0x3B, BCNT = 1, DATA = status`. Built in a stack
   buffer; never touches `s_resp_buf` or the `s_resp_*` state. The last-sent time and
   status change only when `tud_hid_n_report` accepted the packet. 50 ms, not 100: the
   threshold is checked only at progress points, so the wire gap is threshold + step
   length (Jan: calls at 0/90/180 ms with a 100 ms threshold send at 0 and 180).
4. `tud_task()`, so the IN transfer completes (TinyUSB frees the endpoint only inside
   `tud_task`) and INIT / CANCEL / other requests are handled exactly as during a touch
   wait today.

The first KEEPALIVE goes out at the first progress call (status change from "none"); the
state resets when `fido_hid_task()` starts a request. The final response is published
inside `dispatch_request()` after the handler's last progress point, and `s_running` is
false before anything is emitted, so no KEEPALIVE follows it. Held one-packet answers
(short slot, resync answer) go out before the response, and a newer INIT on a channel
supersedes an unsent answer to an older one (Jan, code review).

### 4.2 Call sites

- **Chip calls:** tropic.c gets `tropic_set_progress_hook(void (*fn)(void))`; the hook is
  called at the top of `tropic_l3_session_ensure()` (before the session-ON early return)
  and between the two handshake steps.
  `main.c` registers `fido_hid_progress` at boot. tropic.c stays free of FIDO code, and
  no call happens *inside* libtropic (no hook in the port layer: Jan's "no libtropic
  re-entry").
- **Touch wait:** `user_presence_check()` calls `fido_hid_progress()` in its loop next to
  the existing `tud_task()`. For an OpenPGP touch wait it is a no-op.

Resulting cadence: KEEPALIVEs only at progress points, so the wire gap is at most
50 ms + the longest step without a progress point (one chip command, the certificate read
of a handshake, a software P-256 operation at pin.c:123/142), plus endpoint backpressure.
Not provable from source; §4.5 measures it.

### 4.3 Dispatch policy additions

- **Debug lt-rpc:** `dispatch_request` in rpc.c also refuses (`LT_RPC_ERR_BUSY`) while
  `fido_hid_is_running()`. Without this, a pump between two chip calls of the PIN kernel
  could run an lt-rpc chip command in the middle of an M&D sequence. Release has no
  lt-rpc; the debug build must stay safe.
- **CCID:** unchanged — APDUs never run from a pump.
- **CANCEL is latched for the running request** (Jan finding 2; reproduced on the host:
  today a CANCEL that arrives before the touch wait is lost and the request waits the full
  timeout). CANCEL on the running CID sets a request-owned latch in user_presence.c
  (`user_presence_cancel()` no longer ignores it outside a wait, and
  `user_presence_check()` no longer clears it on entry). A check that starts with the
  latch set returns UP_CANCEL at once → CTAP2_ERR_KEEPALIVE_CANCEL. `fido_hid_task()`
  clears the latch before and after every request, so it never reaches another request or
  an OpenPGP touch wait. Steps without a touch (PIN reservation / re-arm / change, record
  publication) are not interrupted and complete normally; CANCEL never rolls anything back.
  CANCEL itself is never answered.
- **INIT on the running CID = resync** (Jan finding 1; reproduced: today the host gets the
  INIT answer and then the stale CBOR answer on the same CID). It sets an "abandoned"
  latch and the cancel latch, and its INIT answer is held. The request runs to the end of
  its non-cancellable work (a touch wait ends at once); while abandoned no KEEPALIVE is
  sent, and when it returns its response is discarded, not published, and the held INIT
  answer goes out instead. INIT on the broadcast CID or another CID: answered at once,
  as today. No chip rollback, no retry.
- **New request during progress:** CHANNEL_BUSY, as during a touch wait (existing gate,
  `s_busy_cid != 0`).

### 4.4 Short-reply backpressure

KEEPALIVEs make the IN endpoint busy more often, so `send_now()` drops more INIT and BUSY
replies. Replace the drop with a one-packet slot: `send_now()` stores the packet if the
endpoint is busy (if the slot is already full, the new packet is dropped — today's
behaviour, now much rarer); `fido_hid_progress()` and `fido_hid_task()` flush the slot
before anything else, and a KEEPALIVE waits while the slot is full.
`ponytail:` one slot; a queue only if captures show drops.

### 4.5 Timing instrumentation (debug build only)

Per request, print to the debug console: CTAP command byte, duration, number of
KEEPALIVEs, largest gap between two *accepted* KEEPALIVEs including the head (request
start → first) and the tail (last → final response), and largest gap between progress
calls. The capture remains the wire evidence. Also gives the per-operation timings the
parked PIN speed-up needs. Compiled out of release (`NIXTROPIC_DEBUG`).

## 5. Tests first (host)

New `tests/host/test_ctaphid.c` with a small `tusb.h` stub (records IN reports, lets the
test toggle endpoint-ready and inject OUT packets from `tud_task`), the mock tick, and a
test `fido_hid_cbor_dispatch` that calls `fido_hid_progress()` on a scripted schedule.

1. Idle / not running: progress sends nothing and does not pump.
2. Running: first call sends PROCESSING on the owner CID; packet format exact (CID, 0xBB,
   BCNT 1, status); next one not before 50 ms (49 ms: no, 50 ms: yes).
3. Status change PROCESSING → UPNEEDED → PROCESSING sends at once.
4. Final response intact and last on the wire; no KEEPALIVE after it.
5. Endpoint busy: KEEPALIVE skipped, sent on the next ready call; nothing corrupted.
6. INIT on another CID during progress: answered (through the slot if the endpoint was
   busy), before the next KEEPALIVE.
7. New CBOR request during progress: CHANNEL_BUSY, never dispatched.
8. CANCEL during processing without a touch: normal answer; CANCEL before the touch wait:
   the wait returns UP_CANCEL at once; the latch does not survive into the next request.
9. Nested progress (progress called from inside the pump): no second send, no recursion.
10. Same-CID INIT during processing, during the touch wait, and while a multi-packet
    response is going out: held INIT answer, stale response never on the wire, no
    KEEPALIVE after the resync.
11. Jitter (calls every 40 ms → no gap > 100 ms), `ready` true but `report` refused (no
    state change), tick wrap-around, short slot kept and overflow dropped, fragmented
    final response intact.

Plus an rpc.c check that lt-rpc answers BUSY while a FIDO request runs. The tropic.c hook
is not host-testable (libtropic); its wiring is proven on hardware by the §4.5 printout
(KEEPALIVE count > 0 on every PIN operation, with a session already open and after a
re-handshake). Then mutants on the new code, cpp-reviewer, Jan.

## 6. Hardware

1. Both builds: FIDO suite 60/60, OpenPGP APDU 42/42, validate-openpgp 16/16, gpg
   end-to-end 7/7 (fresh card for the APDU suite).
2. Debug build: timing printout for getPinUvAuthToken, changePIN, setPIN, MakeCredential
   with touch, GetAssertion, credMgmt (a full 29-record scan), Reset, the first request
   after boot (handshake) and after a dropped session (re-handshake), and an error path.
   Largest KEEPALIVE gap: interim target ≤ 250 ms (the specification recommends 100 ms).
3. Windows 11 VM with usbmon capture: Settings PIN change; browser register + sign-in
   with PIN; delayed touch (~5 s); cancel during touch. Capture shows KEEPALIVE cadence,
   status, CID. Check which PIN is current before retrying after any failure. If the
   capture shows a same-CID INIT during a long operation: the held INIT answer must not
   make Windows give up (cpp-reviewer); if it does, answer INIT at once and keep
   discarding the stale answer.
